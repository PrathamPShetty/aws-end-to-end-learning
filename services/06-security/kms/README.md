# AWS KMS (Key Management Service)

## What is it?
AWS KMS (Key Management Service) is a fully managed service for creating and controlling the cryptographic keys used to encrypt and decrypt your data. Instead of managing raw key material yourself, KMS stores your keys in hardware security modules (HSMs) and exposes simple API calls to encrypt, decrypt, sign, and verify data. Every major AWS service (S3, EBS, RDS, Secrets Manager) integrates natively with KMS so you can protect data at rest with a single flag. The main benefit is centralised, auditable key management — every use of a key is logged in AWS CloudTrail.

## Key Concepts
- **CMK (Customer Master Key) / KMS Key** — The primary resource in KMS; a logical key that never leaves the service in plaintext. Can be AWS-managed or customer-managed.
- **Key ID / Key ARN** — Unique identifiers for a KMS key; used in all encrypt/decrypt API calls.
- **Alias** — A human-readable name (e.g., `alias/my-app-key`) mapped to a Key ID so code doesn't hard-code key IDs.
- **Data Key** — A symmetric key generated by KMS (`generate-data-key`) for envelope encryption; you encrypt data locally with it.
- **Envelope Encryption** — The pattern of encrypting data with a data key, then encrypting the data key with a CMK; used by S3, EBS, and most AWS services.
- **Key Policy** — A resource-based policy attached directly to a KMS key controlling who can use or administer it.

## When to Use
- Encrypting sensitive database fields, S3 objects, or EBS volumes so they are unreadable without the corresponding KMS key.
- Rotating encryption keys annually (or more frequently) without re-encrypting data — KMS handles key versioning automatically.
- Signing JWTs, documents, or code artifacts with an asymmetric KMS key to prove authenticity.
- Enforcing compliance requirements (HIPAA, PCI-DSS) that mandate customer-managed encryption keys with audit trails.

## CLI Quick Reference (awslocal)

### Key Lifecycle
| Operation | Command |
|-----------|---------|
| Create symmetric key | `awslocal kms create-key --description "app-encryption-key" --key-usage ENCRYPT_DECRYPT` |
| Create asymmetric key | `awslocal kms create-key --key-spec RSA_2048 --key-usage SIGN_VERIFY` |
| List keys | `awslocal kms list-keys` |
| Describe key | `awslocal kms describe-key --key-id <key-id>` |
| Schedule key deletion | `awslocal kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 7` |

### Aliases
| Operation | Command |
|-----------|---------|
| Create alias | `awslocal kms create-alias --alias-name alias/my-key --target-key-id <key-id>` |
| List aliases | `awslocal kms list-aliases` |
| Update alias | `awslocal kms update-alias --alias-name alias/my-key --target-key-id <new-key-id>` |
| Delete alias | `awslocal kms delete-alias --alias-name alias/my-key` |

### Encryption / Decryption
| Operation | Command |
|-----------|---------|
| Encrypt | `awslocal kms encrypt --key-id alias/my-key --plaintext "MySecret"` |
| Decrypt | `awslocal kms decrypt --ciphertext-blob <base64-blob>` |
| Generate data key | `awslocal kms generate-data-key --key-id alias/my-key --key-spec AES_256` |

## Example Walkthrough

1. **Create a symmetric KMS key for encryption/decryption**
   ```bash
   KEY_ID=$(awslocal kms create-key \
     --description "demo-app-encryption-key" \
     --key-usage ENCRYPT_DECRYPT \
     --query 'KeyMetadata.KeyId' \
     --output text)
   echo "Key ID: $KEY_ID"
   ```
   Creates a new customer-managed KMS key and captures its ID.

2. **Create a human-readable alias for the key**
   ```bash
   awslocal kms create-alias \
     --alias-name alias/demo-app-key \
     --target-key-id "$KEY_ID"
   ```
   Maps the alias `alias/demo-app-key` to the raw key ID — now code can reference the alias instead of the ID.

3. **Encrypt a plaintext value using the alias**
   ```bash
   CIPHERTEXT=$(awslocal kms encrypt \
     --key-id alias/demo-app-key \
     --plaintext "SuperSecretPassword" \
     --query 'CiphertextBlob' \
     --output text)
   echo "Ciphertext (base64): $CIPHERTEXT"
   ```
   Returns a base64-encoded ciphertext blob. The original plaintext cannot be recovered without calling KMS decrypt.

4. **Decrypt the ciphertext blob back to plaintext**
   ```bash
   DECODED=$(awslocal kms decrypt \
     --ciphertext-blob "$CIPHERTEXT" \
     --query 'Plaintext' \
     --output text | base64 --decode)
   echo "Decrypted: $DECODED"
   ```
   KMS identifies the correct key from metadata inside the blob — no key ID needed at decrypt time.

5. **Generate a data key for envelope encryption**
   ```bash
   awslocal kms generate-data-key \
     --key-id alias/demo-app-key \
     --key-spec AES_256 \
     --query '{PlaintextKey:Plaintext,EncryptedKey:CiphertextBlob}'
   ```
   Returns both a plaintext AES-256 key (use it to encrypt data locally, then discard) and an encrypted copy (store alongside the data).

6. **Describe the key to verify its state**
   ```bash
   awslocal kms describe-key --key-id "$KEY_ID" \
     --query 'KeyMetadata.{State:KeyState,Usage:KeyUsage,Spec:KeySpec}'
   ```
   Shows the key state (`Enabled`), its usage, and its spec — useful for confirming the key is active.

## Important Flags & Options

| Flag / Parameter | Description |
|-----------------|-------------|
| `--key-id` | Key ID, Key ARN, or alias (e.g., `alias/my-key`) |
| `--description` | Human-readable description stored with the key |
| `--key-usage` | `ENCRYPT_DECRYPT` or `SIGN_VERIFY` |
| `--key-spec` | Key type: `SYMMETRIC_DEFAULT`, `RSA_2048`, `ECC_NIST_P256`, etc. |
| `--plaintext` | Plaintext to encrypt (string or `fileb://file.bin` for binary) |
| `--ciphertext-blob` | Base64-encoded ciphertext to decrypt |
| `--pending-window-in-days` | Days before a scheduled key deletion takes effect (7–30) |
| `--alias-name` | Alias string; must start with `alias/` |
| `--query` | JMESPath expression to filter CLI output |
